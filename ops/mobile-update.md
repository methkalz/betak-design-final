# تحديث نسخة الموبايل

## الحقيقة التي تحكم كلّ ما بعدها

**التحديث اللاسلكيّ لا يصل إلى بناءٍ لم يحمله أصلًا.** الآليّة
(`expo-updates`) تُدمج في التطبيق لحظةَ بنائه، فأيّ نسخةٍ مثبَّتة على هاتفٍ
اليوم لن تستقبل شيئًا مهما فعلنا - يجب أن يُبنى التطبيق **مرّةً** ويُثبَّت،
وبعدها وحدها تعمل التحديثات اللاسلكية.

فالخطوات ٣-٦ تُنفَّذ مرّةً في العمر. والخطوة ٧ هي كلّ ما يتكرّر.

---

## ما جُهّز في المستودع (لا يحتاج منك شيئًا)

- `expo-updates` مثبَّتة - قناة التحديث اللاسلكيّ
- `runtimeVersion: { policy: "appVersion" }` - **حاجزُ أمان**: التحديث
  اللاسلكيّ لا يصل إلا إلى بناءٍ يحمل نفس `version`. فترقيةٌ تحتاج شيفرةً
  أصليّة جديدة لا تهبط على بناءٍ قديم فتُعطبه
- `eas.json` بثلاث لوحات: `development` و`preview` (ملفّ APK للتوزيع
  الداخلي) و`production` (حزمة متجر)
- هويّة التطبيق نُظّفت من سقالة Rork (انظر أسفله)
- أوامرُ مختصرة في `package.json`

### ✅ ١-٤ منفَّذة (23.8.2026)

الحساب `qinova` أُنشئ، والرمز الشخصيّ مضبوطٌ في متغيّر البيئة `EXPO_TOKEN`
على جهاز المالك، والمشروع مربوط، وقناة التحديث موصولة:

| | |
|---|---|
| الحساب المالك | `qinovas-team` |
| معرّف المشروع | `ee2f9955-f081-4a83-a503-c36e805a0508` |
| عنوان التحديثات | `https://u.expo.dev/ee2f9955-…` |
| `slug` | `qinova` (اسم المشروع على expo.dev) |

**لماذا الرمز لا كلمة السرّ**: الحساب أُنشئ بحساب Google، فلا كلمة سرّ له
أصلًا و`expo login` يطلب اسمًا وكلمة سرّ. الرمز الشخصيّ هو الطريق الرسميّ
لحسابات SSO، وهو نفسه ما تستعمله خوادم البناء - ويُبطَل وحده دون مساس بالحساب.

### ٥) البناء الأوّل - يبقى على المالك

```bash
cd expo && bun run build:android
```

يبني على خوادم EAS (لا يحتاج أدواتٍ على الجهاز) ويعطي رابط تنزيل APK.
ولـiOS: `bun run build:ios` - يحتاج حساب Apple Developer مدفوعًا.

### ٦) التثبيت على الهواتف

نزّل الـAPK من الرابط وثبّته على أجهزة الطاقم. **هذه آخر مرّةٍ يثبّتون فيها
شيئًا يدويًّا** ما دام التغيير في شيفرة JS وحدها.

### ٧) وهذا كلّ ما يتكرّر بعدها

```bash
cd expo && bun run update:preview
```

ثوانٍ، ويصل التحديث إلى كلّ هاتفٍ عند فتح التطبيق التالي. بلا متجر، بلا
إعادة تثبيت، بلا انتظار مراجعة.

## فحص أذونات التطبيق المبنيّ

**الأذون لا تأتي من `app.json` وحده**: كلّ حزمةٍ أصليّة تدمج مانيفستها في
مانيفست التطبيق. لرؤية ما سيطلبه التطبيق فعلًا:

```bash
cd expo && bunx expo config --type introspect --json
```

ثمّ اقرأ `_internal.modResults.android.manifest.manifest["uses-permission"]`.
سطرٌ عليه `tools:node: "remove"` يُسقطه دامجُ المانيفست في Gradle فلا يصل
التطبيق.

المفروض أن يطلب التطبيق هذه وحدها: `INTERNET` · `VIBRATE` ·
`READ/WRITE_EXTERNAL_STORAGE` · `FOREGROUND_SERVICE` · `SYSTEM_ALERT_WINDOW`.

ويقفل `domain/appPermissions.test.ts` النيّة في كلّ `bun test`.

## متى لا يكفي التحديث اللاسلكيّ

يحمل JS وحدها. يلزم بناءٌ جديد (خطوة ٥) حين:

- تُضاف حزمةٌ فيها شيفرة أصليّة (`expo-*` جديدة، أو أيّ native module)
- تتغيّر أذونات، أو الأيقونة، أو شاشة البداية، أو اسم التطبيق
- ترتفع `version` في `app.json`
- تُرقّى نسخة Expo SDK

التسعير والشاشات والمنطق - كلّها JS، فتذهب لاسلكيًّا.

## ما بقي مفتوحًا

**`expo-doctor` يعطي 17/18.** المتبقّي تكرارُ حزمٍ **بالنسخة نفسها**
(`expo-constants@18.0.14` في ثلاثة مواضع) - أثرُ رفعٍ من bun لا تعارضَ نسخٍ،
ولا يعطّل بناءً.

**`react-native-maps` مسحوبةٌ بالتبعية** عبر `@rork-ai/toolkit-sdk` ولا
يستوردها سطرٌ واحد. أذونُها محجوبة، لكنّ شيفرتها الأصليّة تبقى في التطبيق
المبنيّ فتزيد حجمه. إزالتها تعني إسقاط `@rork-ai/toolkit-sdk`، وهو يكسر
أوامر `start` في `package.json` - تنظيفٌ مستقلّ.

**`slug` صار `qinova`** لا `betak-design`: يجب أن يطابق اسم المشروع على
expo.dev، و`eas init` كتبه فوق اختيارنا. تجميليّ - لا يمسّ هويّة التطبيق
(`com.betakd.app`). لتغييره: أعِد تسمية المشروع من لوحة expo.dev ثمّ حدّث
`slug` هنا.

**وأُزيلت `expo-location`**: لم تكن مستعملةً في سطرٍ واحد، وملحقُها يضيف إذن
الموقع - تطبيقٌ يطلب إذنًا لا يستعمله يخسر ثقة المستخدم ويستوقف مراجعة المتجر.
