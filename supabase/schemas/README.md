# المخطط التصريحي — مصدر الحقيقة للبنية

هذه الملفات **مُولَّدة من القاعدة الحية** عبر `pg_get_functiondef` و
`pg_get_viewdef` و `pg_dump` — لا مكتوبة من الذاكرة ولا منسوخة من الترحيلات.

## النموذج الهجين — ولماذا هو ضرورة لا تفضيل

| | يديره |
|---|---|
| الأنواع · الجداول · الأعمدة · القيود · الفهارس | `schemas/` |
| أجسام الدوال والviews · triggers · التعليقات | `schemas/` |
| **الملكية (`ALTER … OWNER TO`)** | **migrations يدوية** |
| **`GRANT` / `REVOKE` وصلاحيات الأعمدة والسكيمات** | **migrations يدوية** |
| **إنشاء الأدوار وعضويتها** | **migrations يدوية** |
| **سياسات RLS الحساسة** | **migrations يدوية** (موجودة هنا للمرجع) |
| **بيانات البذرة و backfills** | **migrations يدوية** |

> ⚠️ **الأخطر:** توثيق Supabase يذكر صراحةً أن `supabase db diff` **لا يتتبّع
> `security_invoker` على الviews**. والـ39 view عندنا تعتمد عليه بالكامل —
> بدونه تُنفَّذ بصلاحيات مالكها وتتجاوز RLS كليًا. لذا الاعتماد على التصريحي
> وحده كان سيُسقط نموذج الأمان **صامتًا**.
>
> بقية ما لا يتتبّعه: ملكية الviews ومنحها، سياسات RLS، صلاحيات الأعمدة
> والسكيمات، الصلاحيات الافتراضية، التعليقات، التقسيمات، و DML.

## ⚠️ الترتيب اعتمادي لا أبجدي

اكتُشف عمليًا أثناء بناء هذه الملفات — الفرز الأبجدي يفشل في موضعين:

| الاعتماد | لولا الترتيب |
|---|---|
| `private.can_see_project` → `private.role_in` | `function private.role_in(uuid) does not exist` |
| `api.inventory_roll_balances` → `api.roll_balances` | `relation api.roll_balances does not exist` |
| سياسات RLS → `private.has_role` | `function private.has_role(...) does not exist` |

الترتيب مفروض في `config.toml` عبر `schema_paths` صراحةً، وداخل كل ملف بترتيب
الاعتماد. **لا تستبدل القائمة بـ`./schemas/*.sql`.**

## دورة العمل

```
1. عدّل الملف هنا
2. supabase db diff -f <name>        ← يولّد migration
3. راجع الناتج يدويًا — وأضف الملكية والمنح التي لن يولّدها
4. supabase db reset                 ← بناء من الصفر
5. شغّل كل مجموعات الاختبار
6. commit المخطط + الـmigration معًا
7. supabase db push
```

**لا تعدّل migration منشورة أبدًا.** الترحيلات القائمة سجل تاريخي غير قابل
للتغيير؛ كل تعديل جديد يولّد ترحيلًا جديدًا.

## التحقق بلا CLI

Docker و Supabase CLI غير مثبَّتين بعد على جهاز التطوير. حتى ذلك الحين، فحص
الـdrift يجري بـ`tests/schema_drift.py`: ينشئ قاعدة مؤقتة على نفس العنقود،
يطبّق هذه الملفات بالترتيب، ثم يقارن بصمة الكتالوج (الأعمدة، القيود، الفهارس،
الviews وخياراتها، بصمات الدوال، الـtriggers، الأنواع) مع القاعدة الحية.

آخر نتيجة: **709 كائنًا متطابقًا — NO DRIFT**.
